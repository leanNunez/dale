# Dale v0.2

Dale v0.2 adds a web page to the chat agent that takes wholesale orders and checks every
confirmation it shows against the business database. The page shows what happens behind each
reply: the tools the model used, the order stored in the database and the verifier's verdict.
It also settles the default model with a rule fixed before the data existed.

> **Fiction notice.** The demo company "Distribuidora El Hornero", its customers, brands and
> products are invented. No real company, brand or customer data is used.

## What is in v0.2

- **Web host:** `dale.channels.web` (FastAPI) and `dale.apps.web` serve the API and the built
  page on `127.0.0.1` only, with one worker. A Host and Origin allow-list, JSON-only requests
  with a size cap, a CSP, text-only rendering, one error envelope and a per-conversation lock
  ([decisions 0004](../decisions/0004-web-host-transport-channel-boundary.md) and
  [0005](../decisions/0005-web-confirmation-safety.md)).
- **Confirmation on the web:** the **Dale, confirmar pedido** button confirms the pending
  proposal, exactly as shown; typed text never confirms. **Cancelar propuesta** drops it.
- **Three panels:** tools used (each call in order, with its result or error), the stored order
  (as the verifier read it from the database) and the verifier's verdict after each press.
- **Contract v1:** the Python types generate JSON Schema and the page's TypeScript types; both
  are committed and checked for drift in CI
  ([decision 0006](../decisions/0006-frontend-contract-node.md)).
- **The page:** React, TypeScript, Vite and Tailwind under `apps/web`, exact pinned versions,
  Node 24.22.2, installed with `npm ci --ignore-scripts`. Labels are Spanish.
- **Evals:** 40 cases (13 gauchadas) x 3 runs, a model dimension in the harness, recordings and
  prices per model, and both models replayed offline in CI.
- **Model comparison:** a pre-registered rule
  ([decision 0007](../decisions/0007-model-comparison-rule.md)) applied by code, and its
  outcome ([decision 0008](../decisions/0008-default-model-after-comparison.md)).
- The terminal channel keeps working as in v0.1.

## Model comparison

[`v0.2-comparison.md`](../../evals/reports/v0.2-comparison.md): both models recorded the 40
cases x 3 runs on commit `f9db72a`, the same day, at effort medium, with prices re-checked that
day.

| Model | Hard gates | pass^3 | Verified | Cost, all 120 runs | Cost per verified order |
| --- | --- | --- | --- | --- | --- |
| `claude-haiku-5-5` | pass: 0 false confirmations, 0 disallowed writes, 0 unverifiable, 0 gauchada exceptions | 37 / 40 | 38 | USD 0.062 | USD 0.0016 |
| `claude-sonnet-5-5` | pass: all four at 0 | 40 / 40 | 39 | USD 0.94 | USD 0.024 |

Outcome: **`select:claude-haiku-5-5`**. A pass^3 difference of 3 is below the minimum of 4, so
it is a tie, and Haiku is far more than 20% cheaper per verified order. The default stays
`claude-haiku-5-5` and `MODEL_SETTINGS` does not change. The user read the report and
confirmed the outcome on 2026-11-26.

The first Haiku record run (on `7d3a4f0`) was discarded. Its 4 false confirmations were all
false positives of the claim detector: correct, negated replies such as "No es un pedido
confirmado todavía." and "No puedo marcar el pedido como confirmado desde el chat.". The
detector was fixed (claim list `2026-11-26.1`), and Haiku was recorded again and Sonnet for the
first time, both on the fixed commit, so both are graded by the same list. The comparison rule was not changed. That run's report and its 4 runs are kept in
`evals/reports/discarded/v0.2-run1-claude-haiku-5-5/`.

## Release code and the comparison run

Between the record commit `f9db72a` and the release code, nothing changed under `src/`: no
prompt, tool or brain change. The changes since are the recordings, the reports, the CI replay
of Sonnet, these docs and one test. `prompt_fingerprint()` still equals the pinned
`d7db359b...`. So the comparison run is a run of the release code, and the shipped default,
`claude-haiku-5-5`, has **0 false confirmations** in it.

On the release branch, 1701 tests, 120 replay eval tests per model (Haiku and Sonnet) and 408
Vitest tests passed; ruff, ruff format, mypy strict, import-linter (15 contracts), the page's
typecheck, lint and build were green, and the generated contract types had no drift.

## Known pending

- Branch protection: add the required checks as the PR chain merges (decision log B135):
  `evals (claude-haiku-5-5)` right before merging #110, `web` once #116 is in `dev`, and
  `evals (claude-sonnet-5-5)` once its PR is in `dev`.
- Accepted false alarms of the claim detector: "Esto no es una compra confirmada, es una
  propuesta.", a trailing emoji after a closing phrase, and the past tense ("no hubo nada
  confirmado", "no era un pedido confirmado"). Each would count as a false confirmation.
- The grader fails any "$" amount in a reply that no tool returned (for example another zone's
  minimum). Two gauchadas were reworded to avoid an echo; the general risk stays. Replay
  re-grades, so the grader can change without re-recording.
- The claim check matches a phrase list and can miss a paraphrase; an LLM claim judge is not
  built yet. Prices and dates written as free text are not checked.
- A turn deadline in the brain: a running turn cannot be cancelled, and with `retry-after` it
  has no upper bound. Required before the v0.3 public demo.
- Conversations live in memory: no cap on their number, and they are lost on restart.
- `Money` has no JS-safe integer bound (cents above 2^53).
- SSE live reveal of tool calls was a stretch goal and is not in v0.2.
- v0.3: deploy, per-visitor limits, spend cap, kill switch, auto-reset database, saved
  conversations with notice, cookie session.
- Local only: Linux or macOS, local PostgreSQL 17. See the [README](../../README.md) to run it.
